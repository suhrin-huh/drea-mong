# Backend 통합 리팩토링 설계 방향

작성일: 2026-10-26  
상태: 전체 방향 수립, 구현 전

## 1. 문서의 목적과 범위

이 문서는 drea-mong 백엔드 리팩토링의 목표, 설계 원칙, 우선순위와 단계별 완료 기준을 정의한다. 각 단계의 클래스 설계, API 명세, 작업 목록, 테스트 시나리오는 진행 시점에 별도 세부 계획으로 작성한다.

대상은 `backend/dreamong`의 Spring Boot 애플리케이션과 관련 DB·Docker 실행 구성이다. 꿈 기록, 광장·댓글, 통계, 인증, 파일·AI 연동, 채팅·방, 알림을 포함한다. 프론트엔드는 API 계약 변경의 영향을 확인하는 대상으로 두며, 이번 문서가 프론트엔드 전면 개편을 의미하지는 않는다.

소스 검토를 바탕으로 작성했으며, 빌드·서버 실행·실제 DB 구조·쿼리 수·외부 서비스 동작은 아직 검증하지 않았다. 코드에서 확인한 문제와 실행 검증이 필요한 사항을 구분하고, 각 단계 시작 전에 현재 상태를 다시 확인한다.

## 2. 목표

1. 인증된 사용자와 자원 소유권을 기준으로 접근 권한을 보장한다.
2. HTTP API 전반에서 예측 가능한 오류 응답과 입력 검증을 제공한다.
3. 외부 서비스 실패와 동시 요청에도 데이터 정합성을 유지한다.
4. 서비스의 책임과 트랜잭션 경계를 명확히 하고 중복을 줄인다.
5. 조회 성능과 실행 환경을 재현 가능한 근거로 개선한다.
6. 기존 팀 구현과 이번 개선 범위를 구분하고, 개선 전후의 증거를 남긴다.

## 3. 현재 상태와 주요 개선 대상

| 영역 | 소스 검토 결과 | 방향 |
| --- | --- | --- |
| 공통 오류 | 공통 JSON, 필터의 일반 문자열, Controller별 예외 처리가 혼재한다. 오류 코드·메시지가 부족하다. | 오류 계약과 처리 경로 통일 |
| 사용자 권한 | 꿈·댓글·통계·알림·파일의 일부 기능이 요청의 사용자 ID 또는 자원 ID를 신뢰하며 권한 검증이 부족하다. | 인증 사용자와 자원별 접근 정책 적용 |
| 관리자 권한 | `@PreAuthorize`가 있지만 메서드 보안 활성화 설정을 소스에서 찾지 못했다. `ADMIN` 권한과 `hasRole` 표현도 맞지 않는다. | 실제 차단 여부 테스트와 권한 표현 정리 |
| JWT | 파싱 실패를 만료되지 않은 것으로 처리하고, 알 수 없는 역할을 관리자에 매핑한다. 토큰 원문 로그와 재발급 중복도 있다. | 검증·역할·재발급·실패 응답 정리 |
| 응답 정보 | 알림 API와 방 생성 이벤트가 엔티티를 직접 반환한다. 사용자 연관관계를 통해 민감 필드가 노출될 가능성이 있다. | 필요한 정보만 담는 DTO와 응답 검증 |
| 파일·이미지 | 반복되는 저장 키와 원본 파일명으로 덮어쓰기가 가능하다. 이미지 검열 전 업로드와 중복 업로드가 있다. | 고유 키, 소유권, 저장 순서와 정리 정책 |
| 외부 API | 실패 문구를 정상 결과로 반환하거나 파싱 실패를 빈 카테고리로 처리한다. 통계 조회에도 AI 호출이 반복된다. | 명시적 실패 처리와 기존 데이터 보존 |
| DB 정합성 | 좋아요·카테고리·연결 중복을 막는 복합 유일 제약이 제공된 엔티티·스키마에 없다. 좋아요 수 갱신에는 경쟁 가능성이 있다. | DB 제약과 동시성 검증 |
| 구조·성능 | 꿈 서비스에 AI·파싱·카테고리·저장 책임이 집중되어 있다. 댓글별 추가 조회와 통계 전체 조회 후 상위 항목 제한이 있다. | 책임 분리, 측정 기반 최적화 |
| 채팅 | 별도 Socket.IO 서버에서 연결 인증, 참여·발신자·강제 퇴장 권한 검증이 부족하다. 방 검증 전에 메시지 이력을 전송한다. | 연결 및 이벤트별 인증·인가 |
| 알림 | 스케줄 실행과 Firebase 설정이 주석 처리되어 있다. 비동기 활성화 설정을 찾지 못했고, 전송 완료 상태 관리도 정리가 필요하다. | 기능 유지 범위와 실행·전송 상태 확정 |
| 실행·테스트 | 테스트 파일이 주석 처리되어 있고 로컬 MySQL 설정에 의존한다. Docker 빌드 단계와 파괴적 초기화 SQL을 점검해야 한다. | 기준선 확보와 재현 가능한 환경 |

실제 정보 노출, 관리자 API 차단 여부, 운영 DB 제약, 초기화 SQL 실행 여부, 동시성 오류 및 쿼리 수는 실행 검증 대상으로 남긴다.

## 4. 공통 설계 원칙

### 4.1 인증·인가

- 행위자는 요청 본문·경로의 `userId` 대신 인증 정보에서 식별한다. 다른 사용자 ID가 필요한 API는 그 목적과 권한을 명시한다.
- 로그인 여부, 관리자 역할, 자원 소유권, 공개 여부를 각각 검증한다.
- 개인 꿈 API는 작성자 전용, 광장 API는 공유된 꿈 조회를 기본 제안으로 둔다. 최종 정책은 권한 표에서 확정한다.
- HTTP와 Socket.IO의 인증 경계를 별도로 검증한다. HTTP 보안 설정이 별도 소켓 서버까지 보호한다고 가정하지 않는다.
- 토큰·민감 개인정보·꿈 원문의 불필요한 로그 출력을 제거한다.

### 4.2 응답·오류 계약

- HTTP API의 오류 기본 구조와 필드 의미를 통일하고, HTTP 상태와 고정된 에러 코드로 원인을 구분한다.
- 프론트엔드는 문구 비교 대신 에러 코드로 동작을 분기한다. 사용자 메시지에는 내부 예외·외부 서비스 자격 증명 등을 노출하지 않는다.
- Controller 예외뿐 아니라 인증 필터, 인증 실패·접근 거절, 입력·타입 변환 오류도 같은 계약에 포함한다.
- 입력 검증 오류에는 필드별 상세 정보를 확장할 수 있다. 예상하지 못한 오류는 서버 로그에 원인을 남기고 일반화된 응답을 제공한다.
- 파일 다운로드 같은 바이너리 성공 응답과 OAuth 리디렉션은 전달 목적을 유지한다. 소켓 오류는 이벤트 방식에 맞추되 에러 코드 체계를 공유한다.

오류 형식의 논의 기준은 다음과 같다. 최종 필드·코드·호환 정책은 1단계에서 확정한다.

```json
{
  "status": "error",
  "data": null,
  "error": {
    "code": "DREAM_ACCESS_DENIED",
    "message": "해당 꿈에 접근할 권한이 없습니다."
  }
}
```

### 4.3 구조·트랜잭션

- Controller는 요청·인증 정보 전달과 응답 변환을 담당한다. 비즈니스 규칙과 저장 조정은 Service에서 처리한다.
- AI, 번역, 검열, 저장소, 알림 전송 등 외부 연동은 테스트에서 대체 가능한 경계로 분리한다.
- 외부 호출 때문에 DB 트랜잭션이 길어지지 않도록 경계를 검토한다. 경계 변경 시 동시 수정과 실패 복구도 함께 고려한다.
- HTTP 응답과 소켓 이벤트에는 목적별 DTO를 사용한다.
- 패키지 이동은 책임 정리가 필요한 범위에서 수행한다. 전면적인 계층·아키텍처 교체는 선행 조건으로 두지 않는다.

### 4.4 데이터·외부 연동

- 애플리케이션의 중복 확인만으로 정합성을 보장하지 않는다. DB 제약과 적절한 동시성 제어를 함께 적용한다.
- AI 파싱·번역 실패를 정상 결과로 저장하거나 후속 생성 요청에 전달하지 않는다. 실패 시 기존 데이터 보존 여부를 명시한다.
- 외부 호출의 시간 제한, 재시도 가능 조건, 비용·중복 실행 방지를 정의한다. 재시도는 유료 생성·업로드 등의 중복 부작용을 고려한다.
- 파일은 고유 저장 키와 소유권을 관리하고, 임시·미사용·실패 파일의 정리 기준을 둔다.
- DB와 외부 저장소·소켓·푸시 사이의 부분 실패를 고려한다. 분산 트랜잭션 등 복잡한 구조는 필요성이 확인된 경우 도입한다.

### 4.5 점진적 변경·검증

- 기능 단위로 변경하고 테스트와 문서를 함께 갱신한다. API·이벤트 계약 변경은 프론트엔드 영향과 적용 순서를 기록한다.
- 기존 실패와 새 변경으로 발생한 실패를 구분한다. 테스트 실행 성공 시 실제 실행된 테스트 수와 범위도 확인한다.
- DB 변경에는 데이터 보존·정리·복구 방안을 포함한다. 유일 제약 추가 전 기존 중복 데이터를 확인한다.
- 성능 개선은 동일한 데이터와 요청 조건으로 비교한다. 측정 전에는 조회 수·응답 시간 개선치를 단정하지 않는다.

## 5. 단계별 로드맵

아래 순서는 기본 흐름이다. 채팅·알림을 실제 운영한다면 해당 권한·정보 노출 문제는 우선 처리 범위로 앞당긴다. 각 단계에는 필요한 회귀 테스트를 포함한다.

| 단계 | 목적·주요 범위 | 완료 기준 |
| --- | --- | --- |
| 0. 실행·검증 기준선 | 빌드·실행 설정, DB·Redis·외부 서비스 의존성, 현재 API·이벤트와 권한 정책 파악 | 실행 절차, 기존 실패 목록, 최소 테스트 실행 환경, 권한 정책 초안 확보 |
| 1. 공통 오류 계약 | 에러 응답·코드·HTTP 상태, 전역 예외 처리, 인증 오류 경로, 입력 검증 기준 | 대표 오류가 동일한 계약으로 반환되고 프론트 영향과 전환 범위가 문서화됨 |
| 2. 인증·관리자 보안 | JWT 검증·역할·재발급, 관리자 검사, 민감 정보 응답·로그 | 비로그인·잘못된 토큰·일반 사용자·관리자 테스트 통과, 민감 필드 반환 방지 |
| 3. 자원별 접근 권한 | 꿈·댓글·통계·알림·파일의 인증 사용자 식별과 자원 접근 정책 | 본인·타인·공개·비공개·존재하지 않는 자원의 허용·거절을 검증 |
| 4. 파일·외부 API 안정성 | 파일 키 충돌, 검열·업로드 순서, AI·번역 실패, 시간·용량 제한, 부분 실패 | 다른 요청의 파일을 덮어쓰지 않고 외부 실패를 성공 처리하거나 기존 데이터를 훼손하지 않음 |
| 5. 데이터 정합성 | 좋아요·카테고리·연결의 제약, 동시 갱신, 연관관계 메서드, 닉네임 정책 | 중복·동시 요청 테스트 통과, 실제 DB 변경과 기존 데이터 처리 절차 확보 |
| 6. 서비스 책임·트랜잭션 | 꿈 AI 분석·파싱·카테고리 분리, 중복 제거, 외부 호출과 DB 작업 경계 | 공개된 동작을 유지하고 외부 실패·카테고리 변경·동시 수정의 정책을 검증 |
| 7. 조회 성능 | 광장 댓글의 반복 조회, 통계 상위 항목 조회, AI 결과 재사용, 필요 시 페이지·인덱스 개선 | 동일 조건의 SQL 수·응답 시간·외부 호출 수 등 개선 근거 확보 |
| 8. 채팅·알림 정비 | 소켓 연결·이벤트 권한, 메시지 검증·보존, 알림 활성화·성공·실패·중복 전송 관리 | 유지하기로 한 기능의 정상·실패 흐름을 통합 검증 |
| 9. 실행·운영 재현성 | Docker 빌드, 버전·환경변수·준비 상태, DB 마이그레이션, 문서·자동 검증 | 깨끗한 환경에서 빌드·실행·테스트·DB 변경을 재현하고 필수 검사를 자동화 |

0단계에서 필요한 최소 실행 복구를 수행하며, Docker·DB 관리 전체 정비는 9단계에서 마무리한다. 5단계 등 앞선 단계에서 필요한 DB 변경부터 마이그레이션 이력을 남긴다. 6단계 이전에도 테스트와 수정에 필요한 최소 책임 분리는 수행할 수 있다.

## 6. 테스트와 개선 근거

| 검증 대상 | 기본 접근 | 남길 근거 |
| --- | --- | --- |
| 비즈니스 규칙·외부 실패 | JUnit·Mockito 기반 단위 테스트 | 권한·실패 정책과 회귀 시나리오 |

| DB 제약·동시성 | MySQL 특성을 반영한 통합 테스트 | 중복 차단, 좋아요 수 정합성, 데이터 변경 결과 |
| 조회 성능 | 고정 데이터와 동일 요청으로 전후 측정 | SQL 수, 데이터 규모, 외부 호출 수, 측정 조건 |
| 파일·채팅·알림 | 경계별 테스트와 필요한 실제 연동 검증 | 파일 격리, 이벤트 권한, 부분 실패·전송 상태 |
| 실행 환경 | 깨끗한 환경에서 빌드·기동·검사 | 사용 명령, 필수 설정, 성공 조건과 제한 |

실제 외부 호출을 사용하는 검증은 비용과 환경 의존성을 명시하고, 일반 테스트에서는 외부 서비스를 대체한다. MySQL 통합 테스트 환경의 구체적인 도구와 자동화 방식은 세부 계획에서 선택한다.

## 7. 단계별 기록 방식

각 단계는 독립적으로 리뷰 가능한 변경 단위로 나누고, 다음 항목을 세부 계획과 결과 문서 또는 PR에 남긴다.

1. 기존 문제와 해당 코드·재현 조건
2. 개선이 필요한 이유와 선택한 정책
3. 변경 범위, API·이벤트·DB·프론트엔드 영향
4. 검증 방법과 실제 결과, 미검증 항목
5. 개선 전후 비교와 남은 한계
6. 기존 팀 구현과 이번에 직접 개선한 범위

기능 수정, 대규모 파일 이동, 의존성 업그레이드는 리뷰 목적에 맞게 나눈다. 기술 버전 교체나 신규 인프라 도입은 별도 근거가 있을 때 범위를 확정한다.

## 8. 후속 세부 계획에서 확정할 사항

- 개인 학습·포트폴리오와 서비스 재운영 중 최종 목표, 채팅·알림의 유지 범위
- 개인 꿈·광장·댓글·통계·파일의 접근 정책과 권한 거절 시 403 또는 존재를 숨기는 404 정책
- 공통 에러 필드·코드 목록, 입력값 제약, 기존 응답과의 전환 방식
- API·소켓 계약 변경에 따른 프론트엔드 수정 범위와 적용 순서
- 액세스·리프레시 토큰 용도, 재발급·로그아웃·쿠키 정책
- 파일 소유권·공개 범위·수명 주기, 외부 실패와 재시도·비용 제한 정책
- 좋아요·닉네임·카테고리의 정합성 기준과 DB 마이그레이션 방법
- 임시 저장과 완료된 꿈의 구분, 문자열 날짜의 타입 전환 필요성
- 테스트 환경, 측정 데이터, 자동 검증 범위와 단계별 구체적인 완료 조건

위 사항은 미확정 항목이며 이 문서만으로 구현 정책이 확정된 것으로 보지 않는다. 다음 작업은 0단계 세부 계획 수립과 실행·검증 기준선 확보다.
